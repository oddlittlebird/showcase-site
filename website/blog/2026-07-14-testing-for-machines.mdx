My portfolio site has an `llms.txt` file. It's not for you.

{/* truncate */}

[`llms.txt`](https://llmstxt.org/) is the emerging convention for giving AI tools a structured, machine-readable map of a site's content. The idea is the same as `robots.txt`, but aimed at language models and AI-assisted search rather than web crawlers. The file describes what the site covers, where the key pages are, and who made it, in plain markdown that a retrieval pipeline or AI agent can fetch and pass along as context without rendering a browser.

Nobody clicks it. Nobody subscribes to it. If it disappears, or drifts out of sync with the site it's supposed to describe, no human notices. An AI agent might start returning wrong information about the site, and nothing in a normal deployment pipeline would catch it, because nothing in a normal deployment pipeline is watching a static file that no human is reading.

That's the problem I wanted to test.

## What to assert

I worked with Claude Code to draft these tests. Basically, I told it what I wanted to test, it built the tests.

When we started with the premise of testing llms.txt, Claude Code proposed checking for the author's name. I pushed back. Most documentation doesn't have a named author, so that's not a meaningful signal, and it doesn't scale.

The more useful assertion is structural. The [`llms.txt` spec](https://llmstxt.org/) requires an H1 title and at least one `##` section heading. Those are format requirements that hold across any site's implementation. A test that asserts on `## ` is true for every valid `llms.txt` and fails the right way: a 200 response that contains no section headings is either a placeholder or a corrupted file, and either way you want to know.

That would test that the llms.txt was valid per the spec, but I wanted to test if llms.txt was correct in terms of _content_.

## Going further without hardcoding

Structural conformance catches a broken or missing file. It doesn't catch drift: a file that was valid six months ago and is still technically valid now, but no longer reflects the site's current shape because sections were added or removed.

A diff between the llms.txt was an option, but outside of Doc Detective's capabilities. Even if it wasn't, that could be a fairly long and intensive test.

Instead, I suggested the test count headings and assert on the count. Claude Code immediately rewrote the test, but it hardcoded the number of headings. I vetoed that, because it wouldn't scale, and asked if we could write a script that counts the number of each heading and stores them somewhere that the test can reference.

Claude Code wrote two items for me:
- A script that runs on every push that touches `llms.txt`, counts the headings by level, and writes the result to a JSON file in the repo.
- A Doc Detective test then fetches the live file, counts the headings, and compares against the stored baseline.

If they match, the test passes. If the file has drifted from its last known-good state, the test fails.

When you intentionally add or remove a section, you update `llms.txt`, the count script runs, the baseline updates, and the test passes again. The test only fails when the live file diverges from what was last committed. The count is never hardcoded anywhere.

This test was a reasonable compromise between diffing for every single word (too granular) and just testing for the presence of certain headings (too vague).

## Making it visible

The [test page](/showcase-site/doc-detective/llms-txt-test) shows the live heading counts alongside the pass/fail badge. That's the same pattern as the pipeline test: don't leave the result buried in a GitHub Actions log where nobody looks until something breaks loudly. Put it next to the thing it's checking.

The heading counts also make the state of the file visible at a glance, independent of whether the test is passing. If the counts look wrong to a human reader, that's useful information regardless of what the automated assertion says.

## The testing surface nobody talks about

Most documentation testing is aimed at human readers: does this page load, does this link resolve, is this image rendering. Those are the things people notice when they go wrong.

`llms.txt` has a different audience. The readers are language models, AI-assisted search tools, and whatever retrieval pipeline sits in front of a chatbot that someone is pointing at your documentation. Those readers don't open issues, don't send error reports, and don't tell you when they got a 404 instead of a file description. They just use whatever they are given, without question.

Testing for that audience requires thinking about what "correct" means from the model's side of the request, not the human's. A test that verifies `llms.txt` is reachable, structurally valid, and hasn't quietly lost sections is a test written for a reader that will never complain if you skip it.

That's the category of test this is: not "does this page render well," but "is this file still describing something true, to a reader who won't tell you when it isn't."
