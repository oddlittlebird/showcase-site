There is a file in this repo called `pipeline.md`. It exists so an AI agent can read a straight description of how this site's documentation pipeline works. It's the file my whole "documentation for machines" argument rests on.

Until last week, it had no front matter. None. It opened on an H1.

Vale read it. Doc Detective read it. Docusaurus built it. Every check passed.

{/* truncate */}

## Adding a third gate

I added [docmeta](https://hawkeyexl.github.io/docmeta/) to the pipeline this week. The split is clean. Vale checks how the prose reads, Doc Detective checks whether the procedures still work, and docmeta checks the metadata. Before this, nothing in my stack looked at front matter at all.

One thing to know before you try it. It needs Node 24. The Get started page says Node 20 or newer, but the package has required Node 24 since its first release, and npm reports that mismatch as a warning rather than an error. So the install says it succeeded, `docmeta --version` answers normally, and the thing quietly doesn't work. I had pinned my CI to Node 22, which would have produced the same silent non-failure. I filed that with the maintainer.

## The first run told me nothing

docmeta ships with schemas for Docusaurus front matter, so I started with those. Thirty files across my docs, blog, and pages directories:

```
30 files checked, 30 passed, 0 failed, 0 errors
```

A clean sweep. Which sounds like good news and is actually the entire problem.

The built-in schema is honest about this in its own description: "Docusaurus marks no field as required, so this is a format check, not a presence check." It constrains the shape of every field Docusaurus accepts, and it requires none of them. A file with no front matter whatsoever satisfies it completely. That's how `pipeline.md` passed.

## Eleven lines changed the answer

So I wrote my own schema. The interesting part is how small it is:

```json
{
  "type": "object",
  "additionalProperties": true,
  "required": ["title", "description", "last_reviewed"],
  "properties": {
    "title": { "type": "string", "minLength": 1 },
    "description": { "type": "string", "minLength": 1 },
    "last_reviewed": { "type": "string", "format": "date" }
  }
}
```

Then I ran it again. Requiring nothing but a title and a description, on a site I built specifically to demonstrate documentation quality:

```
24 of 30 files failed
```

Six passed. All six live in `src/pages`. Not one file in `docs/` or `blog/` had a description. Fifteen blog posts, zero descriptions, every one of them written by someone who does this for a living.

`description` is the field that feeds search results and AI retrieval. It had been missing from almost everything for months, and no gate I owned had any opinion about it.

## The date that is not a date

Here is the part that convinced me this belongs in the pipeline permanently.

I made a test file with a title, a description, and `last_reviewed: 2024-13-45`. Month thirteen, day forty-five. Against the Docusaurus schema:

```
1 file checked, 1 passed, 0 failed, 0 errors
```

Against my schema:

```
/last_reviewed  must match format "date"  (line 4)
```

Exact field, exact line. That gap is the whole argument. If I ever build a staleness report on `last_reviewed`, the report doesn't error when the field is garbage. It just quietly returns a wrong answer, and the wrongness looks exactly like an answer.

## Two things I got wrong

**The check that would never have run.** I wired docmeta into my existing lint workflow and nearly shipped it broken. That workflow triggers on changes to content paths: `website/docs/**`, `website/blog/**`, and so on. My change touched only the config file, the schema, and the workflow itself. None of those matched, so the workflow would never have run at all. Not failed. Skipped. I would have had a green pull request, a check that never ran, and no way to tell the difference from the outside. A check that doesn't run is worse than no check, because the green tick still shows up.

**A rule that had been failing invisibly.** While fixing the first problem, Vale started complaining about spaced em dashes in a line I had just added. I went looking and found that same rule was already firing fourteen times in `pipeline.md`, on text that has been sitting there for months. I had never seen it, because reviewdog only comments on lines inside the diff. Those lines had not changed since the rule landed, so the errors were real, error level, and completely invisible. My linter had been finding things and telling nobody.

## What I actually changed

Descriptions on every published page. Front matter on `pipeline.md`, finally. Both new files committed to the repo, so the schema and config are as open to inspection as everything else here.

One decision worth calling out: I seeded `last_reviewed` from each file's last commit date, not from today's date. Stamping today would have asserted that I reviewed twenty-eight files, which I didn't. I read them. That's a different claim, and writing the stronger one into metadata would have been the exact failure this check exists to catch, committed on day one by the person installing the check.

I also stopped validating two files: the starter blog posts Docusaurus ships with, still sitting in my repo full of placeholder text. Docusaurus already excludes them from the build. Writing descriptions for pages nobody publishes would have been inventing metadata to satisfy a number. The first thing the new check changed wasn't a file. It was the scope of what gets checked.

The result:

```
28 files checked, 28 passed, 0 failed, 0 errors
```

## What it cost

Under two minutes of setup, including reading the list of built-in schemas. The schema is eleven lines. That's the part that bothers me. This wasn't hard, and it wasn't expensive, and I didn't do it for months, because everything was passing and nothing was complaining.

An unchecked field doesn't announce itself. It sits there looking exactly like a checked one.
