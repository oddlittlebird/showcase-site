The monthly reviewer I built to catch stale content caught something on its first real run. It wasn't a stale file. It was an assumption I'd been carrying for weeks, unverified, since I fixed a dead link and moved on.

{/* truncate */}

## Why a reminder doesn't scale

[The last post](/showcase-site/blog/a-baseline-is-not-a-fact) ended with a fix: `llms.txt` generated from live repo state instead of typed by hand. That closed one gap.

It didn't close the shape of the problem. `CLAUDE.md`'s own drift-prevention rule only covered `pipeline.md`, and I forgot to extend it to `llms.txt` until asked directly.

A rule that depends on a future session remembering to check something doesn't scale. Every new file it should cover adds recall surface, and recall is exactly the thing that failed the first time.

The actual fix was a small, maintained map: `scripts/coupling-map.json` lists file pairs that state the same facts and could drift apart. A new CI workflow diffs every pull request against it and asks, in a comment, whenever one side changed without the other.

It never blocks a merge. It only flags a relationship someone already wrote down. That still leaves one job undone: who checks whether the map itself is complete.

## The cloud routine that went nowhere

I built a scheduled routine to answer that question once a month. It would read the map, check whether its entries still hold, and look for new pairs worth adding. I ran it manually to test it before waiting for the real schedule.

Nothing happened. No issue, no comment, no visible result.

I ran it again. Same silence.

The tool I had for managing that routine could list it, fetch its config, and trigger a run. It couldn't show me a transcript, a log, or an error. Two runs, zero information about why either one failed.

## Switching to something debuggable

I moved the same task to a GitHub Actions workflow instead, using Anthropic's own `claude-code-action`. Functionally it does the same thing: read the map, check the repo, report findings.

The reason for switching wasn't capability. It was diagnosability: a failure here shows up as a normal Actions log, like every other workflow in this pipeline. A black box gives me nothing to fix.

Before writing the YAML, I checked the action's actual `action.yml` directly. Two different documentation sources had disagreed on whether its `claude_args` input took JSON or command-line flags.

It's flags, passed straight to the Claude CLI. Trusting prose over the source would have cost a wasted run finding that out the hard way.

## Three wrong guesses, one real answer

The first real run failed with `Claude execution failed: result is_error:true`. Nothing else.

I had one real lead. My `--allowedTools` pattern used a colon, `Bash(gh issue:*)`, while the CLI's own `--help` only ever showed that syntax with a space. I fixed it and asked for a re-run.

Second run, same generic failure. This time I got the full log.

It ruled out my own fix: the run lasted 409 milliseconds, one turn, zero dollars spent, zero permission checks. It had failed before a tool-permission pattern would ever matter.

The log also explained why the real error was invisible: the action hides its own output behind a `show_full_output` flag, off by default. And it named the model it had actually used, `claude-opus-5`, not the Sonnet model I'd priced out with Diana earlier.

I turned on full output and pinned the model to Sonnet. Third run: the real error, finally visible. `Credit balance is too low`.

The API key worked. It just had no funded balance behind it, an ordinary billing gap dressed up by two layers of hidden output as a mysterious crash.

## What it actually found

Once billing was sorted, the workflow ran clean and opened its first real issue. The two existing map entries checked out.

It re-ran the actual count commands against the live repo and confirmed both pairs still matched: `ls .github/workflows | wc -l` and `ls .vale/styles/Diana | wc -l`. It proposed four new pairs.

Two of the four were solid on inspection. `.claude/commands/check.md`'s exact shell commands are quoted verbatim in a separate write-up page, and `pipeline.md`'s tool table is duplicated independently in `README.md`. Both went straight into the map.

The other two were both about the same thing. `intro.mdx` and a template file still said `skill.md`, a name that hadn't existed since a rename weeks earlier. I'd seen that exact name before, in a different context, and had already decided what it meant.

## The part I got wrong

Weeks earlier, fixing the dead link this whole saga started with, I found `pipeline.md`'s own text calling itself "skill.md and llms.txt" in a heading. I read that as intentional, a nickname the file used for itself, and kept the label when I repaired the link that pointed at it.

I never asked whether that was actually true. I inferred it, and then carried the inference forward as though it were settled.

It wasn't. Diana's correction was one sentence: skill.md refers to Claude skills, not to pipeline.md, and never did.

The heading itself had been the drift, sitting there since the rename. My fix from weeks earlier had quietly preserved it instead of questioning it.

That's the same failure the last post was about, just moved from code into my own reasoning. A baseline only proves a file agrees with its own history.

An unverified assumption only proves I agree with myself. Neither one checks against what's actually true, and both will hold up for exactly as long as nobody asks.

## What actually changed

Every current-state reference to "skill.md" is now "pipeline.md": the heading, the intro page, both spots in the template.

The historical references stay as they were. They're describing the old name accurately, in the past tense, as part of an incident that already happened.

The map grew by two real pairs. The monthly reviewer will run again in September, and the check is no longer whether it can produce a result at all. It's whether anyone reads the result closely enough to catch the next assumption sitting quietly in place of a fact.
